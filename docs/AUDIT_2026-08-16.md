## 一、Critical 问题（必修）

### C1：源代码层无实质内容，违反项目定位

**证据：**
```rust
// src/main.rs
fn main() {
    println!("Hello, world!");
}
```
```toml
# Cargo.toml
[package]
name = "ericstack"
version = "0.1.0"
edition = "2021"
[dependencies]    # 空
```
```toml
# Cargo.lock — 仅 ericstack 一个条目，无任何外部依赖
[[package]]
name = "ericstack"
version = "0.1.0"
```

**问题：**
- EricStack 自我定位为"AI-native engineering loop"，但项目自身仅是一个空 Rust crate
- `erics-stack` / `estack` / `ericstack` / `loopx` 4 个词都是抽象的 skill 系统品牌，**没有任何被这些 skill 操作的具体业务代码**
- 即便 docs/APS_INTEGRATION.md 提到"项目代码 / step handlers"，src/ 中无可被 step handler 操作的代码
- 用户安装 `install-ericsstack.sh` 后，得到的是空 crate + 38 个 SKILL.md

**风险：**
- 用户无法验证 skill 是否真正能操作代码
- Skill 中的所有示例代码（`src/auth/step_handlers.py`）都是虚构引用
- 与"AI-Era TDD 闭环"的承诺不符 — 没有可 TDD 的代码

**修复路径：**
- **方案 A（推荐）：** 接受 EricStack 是"skill 元项目 + 工具集"定位，README 明确说明"src/ 是 placeholder，欢迎贡献示例项目"
- **方案 B：** 添加一个完整可运行的 demo（如 `examples/auth-service/` — Python/Go/Rust 任一），让 acceptance pipeline 有真正可操作的代码
- **方案 C：** 把 src/ 改为文档站点构建器（如 mdbook），让 EricStack 自举其自己的文档

**问题：**

**风险：**

**修复路径：**

- **中期：** fork unclebob 仓库，本地构建 BB 脚本 + Go 二进制
- **长期：** 重写为纯 Python 实现（`pip install ericstack-aps`），不依赖 BB

## 二、High 问题

### H1：LoopX status contract 失败，goal state 不一致

**证据：**
```yaml
# loopx status 输出
status.ok: False
contract.errors: 1
status_contract.errors:
  - error: registry boundary risk: registry_tracked_but_not_push_allowed
```

```yaml
# registry.json
coordination.requires_parent_approval: ["write", "publish", "production-action"]
spawn_policy.allowed: false
```

**问题：**
- `read_only_project_map_v0:connected-read-only` 状态说明适配器只读
- 但 ACTIVE_GOAL_STATE.md 列出 5 个 agent_todos（其中 3 个 open），包括 "Run loopx check"
- 适配器只读 + goal 计划 todo = 矛盾
- 当前对话已执行了 `write docs/APS_INTEGRATION.md`、`write docs/AUDIT_2026-08-16.md` — registry 不知道这些写入
- 提示中 `attention_queue.loopx-contract: contract_check_failed phase=None waiting_on=codex severity=high` 是阻塞信号

**风险：**
- LoopX contract 持续失败，未来 todo 完成无法被记账
- promotion readiness gate 标 `freshness=missing`，无法升级
- `attention_queue.needs_codex=2` 表示 codex 应处理

**修复路径：**
- 切换 adapter：`adapter.kind = "guided_project_loop_v0"` 或类似可写版本
- 或在 user_todo 中显式标记 "skill 内容审计 + 文档增强" 类任务为 read_only
- 或修复 registry 的 `requires_parent_approval` 列表，移除非阻塞项

### H2：Skill frontmatter 触发词覆盖率不足

**证据：**

| 类型 | 计数 | 状态 |
|---|---|---|
| `erics-process-*` 有 triggers | 13/13 | ✅ |
| `erics-ability-*` 有 triggers | 24/24 | ✅ |
| `erics-loop-router` 有 triggers | 1/1 | ✅ |

但 **description 字段质量参差不齐**：
- 最佳：`erics-process-acceptance-pipeline`（具体到 7 阶段 + 强制门禁）
- 最弱：`erics-ability-investigate`（43 行，仅有"Four-phase debugging"）

**问题：**
- 一些 skill 的 description 是从上游 copy-paste（如 `erics-process-doc-standards`、`erics-process-prose-standard`），未针对 EricStack 本地化
- trigger 命名不一致：有的用动词（`graft`, `simplify`），有的用名词短语（`merge stacked prs`, `find simplifications`），影响 LLM 路由
- 中文 trigger 与英文 trigger 混杂，可能导致 LLM routing 时歧义

**修复路径：**
- 跑一次 description 质量检查：每个 description 必须 ≤ 150 词，必须包含 "Use when" 触发条件，必须引用具体能力
- trigger 标准化：英文 lowercase + 空格（无下划线/连字符），中文 ≤ 4 字
- 抽取 frontmatter lint 到 `sync-skills.sh --check`

### H3：acceptance.env 与 v1.1 文档不一致

**证据：**

```
acceptance.env（实际）：
APS_MUTATION_SURVIVAL_RATE_MAX=5      ← 单阈值 5%
APS_FRAMEWORK=auto                    ← auto 模式
APS_PLACEHOLDER_VARIANT_THRESHOLD=3   ← 仅一个 placeholder 阈值
```

```
docs/APS_INTEGRATION.md v1.1（声称）：
- 分级门禁 <3% / 3-8% / 8-15% / >15%
- 支持 8 个框架 (JUnit5, Pytest, Behave, Jest, RSpec, Go testing, vitest, Kotest)
- TTL 7 天
- 多类退出码 (0/1/2/3/4/130)
```

**问题：**
- 配置文件没有跟上文档演进 — v1.1 新增的 4 项特性（分级门禁、TTL、扩展退出码、插件 hooks）acceptance.env 一个也没配置
- 即便 APS 工具可用，配置也只能跑出 v1.0 行为
- 5% 单阈值会阻止任何存量项目首次通过（v1.1 已发现并修复）

**修复路径：**
- 把 acceptance.env 升级为 YAML 格式支持嵌套（`mutation.warn_threshold: 8`，`mutation.block_threshold: 15`）
- 或拆分为多文件：`acceptance.env`（基础）+ `mutation.yaml`（门禁）+ `cache.yaml`（缓存策略）

### H4：sync-state.json 与真实目录不对应

**证据：**

| 来源声称 | 实际 |
|---|---|
| deepseek-harness: 11 skills | 目录中有 13 个 `erics-process-*` |
| gstack: 15 skills | 目录中 24 个 `erics-ability-*` |
| 本地新增: 未标注 | 至少 4 个本地新增（acceptance-pipeline, mutation, bdd, test-runner, estack, estack-upgrade, loop-router） |

**问题：**
- sync-state.json 的"上游来源"元信息失真 — 它声称只从两个上游同步，但实际有大量本地新增 skill
- 这破坏 `sync-skills.sh` 的"检测上游更新"逻辑：脚本无法识别哪些 skill 该被 sync，哪些该被保护
- 未来从上游 sync 时，本地自定义 skill 可能被覆盖

**修复路径：**
- 添加 `local` 来源条目：`"local": { "skills": [...], "last_modified": ... }`
- sync-skills.sh 在写入前对比 hash，相同则跳过；不同则报警
- 加 `protected_skills: ["erics-process-acceptance-pipeline", ...]` 字段

### H5：install 脚本无幂等性 / 无 dry-run

**证据：** `install-ericsstack.sh`、`install-acceptance-pipeline.sh`、`uninstall-ericsstack.sh` 均未检查 `set -e` 之外的副作用。

**问题：**
- 重复运行 `install-ericsstack.sh` 行为未定义（创建 ~/.claude/skills 还是覆盖？是 symlink 还是 cp？）
- 没有 `--dry-run` 模式，调试时必须真实操作
- 卸载脚本（uninstall）声称"remove 40 skills"，但当前实际 38，数字错误

**修复路径：**
- 所有 install/uninstall 脚本添加 `--dry-run` / `--force` / `--check` 三态
- 卸载脚本动态计算 skill 数（`find ... | wc -l`）而非硬编码 40
