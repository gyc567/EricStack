## 4. 剩余阻断与风险

### Critical 1：GitHub Actions 尚未进入 Git 历史

**证据：**

- `git status --short .github` 返回 `?? .github/`。
- origin `https://github.com/gyc567/EricStack.git` 可达，remote/local HEAD 均为 `7f381012d34fb799720b6dbd97f9a14882aa5182`。
- `git ls-tree -r --name-only origin/main` 没有 `.github/workflows/`。
- 已认证的 `gh workflow list --all` 和 `gh run list --limit 10` 均无输出。

当前工作区 workflow 已完善且本地 YAML 验证通过，但 GitHub 远端实际没有 workflow 或 run。发布或合并前必须把 `.github/workflows/ci.yml` 与 `skill-validate.yml` 纳入提交，并观察一次 hosted run。

### Critical 2：多个核心 Skills 引用未随仓库提供的运行时资产

缺失的唯一 helper 命令：

- `bin/erics-brain-cache`
- `bin/erics-first-task-detect`
- `bin/erics-redact`
- `bin/erics-repo-mode`
- `bin/erics-review-read`
- `bin/erics-session-kind`
- `bin/erics-taste-update`
- `bin/erics-update-check`

缺失的必读附属内容：

- `references/examples.md`
- `references/recall-batteries.md`
- `sections/audit-phases.md`
- `sections/proposal-and-preview.md`
- `sections/review-sections.md`

这会直接影响 `spec`、`office-hours`、`plan-eng-review`、`cso`、`design-consultation`、`devex-review`、prose/CoT 等工作流。部分命令有 fallback，但被标为 `STOP/Read ... and execute it` 的 sections 没有安全 fallback。

### Critical 3：APS 仍是 gated skeleton，无法做端到端验收

- `APS_TOOL_AVAILABLE=false`。
- `gherkin-parser`、dry checker、generator、mutator 二进制未随仓库提供。
- 本轮只能验证配置和安装器，无法运行文档声称的七阶段真实管道。

默认关闭门禁是正确缓解，但在提供并校验工具前，不能宣称 APS 已可用。

### Critical 4：LoopX registry 边界契约失败且含本机绝对路径

实际命令：

```text
loopx --registry .loopx/registry.json check --scan-root /Users/jie/code/EricStack
ok: False
error: registry boundary risk: registry_tracked_but_not_push_allowed
```

registry 还包含：

- `/Users/jie/.codex/loopx`
- `/Users/jie/code/EricStack`

LoopX 0.4.3 的契约明确把 runtime registry 定义为不应 push 的本地控制面。推荐将运行时 registry 从 Git 历史移出并加入 `.gitignore`，另提供去隐私化 example fixture。此动作涉及 Git 跟踪边界，本轮未代用户执行 `git rm --cached`。

### High 1：Skill body 仍有 24 个非代码块 Markdown 相对断链

主要指向未导入的上游 `notes/`、`references/` 资产，包括：

- `../../notes/README.md`
- 多个 `../../notes/implemented/...`
- `references/examples.md`
- `references/recall-batteries.md`

Wiki 链接已修复并纳入 CI，但普通 Markdown 链接尚无 CI checker。不能简单删除这些链接，因为其中部分是 Skill 工作流的证据和必读校准材料，应选择“导入资产”或“重写为自包含规则”。

### High 2：同步供应链策略与实现仍不一致

`.loopx/sync-state.json` 声明 `checksum_verify: true`，但同步器没有 checksum/签名验证。`--execute` 直接拉取 public upstream HEAD，做 sed 后写入本地。确认门禁和网络 fail-closed 已修复，但仍建议：

1. clone 后显式 checkout 已解析 commit；
2. 验证实际 `HEAD == remote_commit`；
3. 对导入文件做 allowlist/checksum；
4. 两个 source 在临时 staging 完成后原子切换，避免部分更新。

### High 3：sync-state 命名与源码目录布局不一致

11 个 ability 源目录使用裸名，例如 `benchmark/`、`spec/`，而 state 和安装后名称使用 `erics-ability-*`。安装器会规范化名称，因此用户安装结果正确，但 state/protection/sync 的名称契约不直观，容易在未来同步时漏保护。应引入机器可读 manifest，明确 `source_name → installed_name → protected`。

### High 4：CI 供应链仍使用浮动 action tag

`actions/checkout@v4`、`actions/cache@v4`、`actions/upload-artifact@v4`、`dtolnay/rust-toolchain@stable` 未 pin 到 commit SHA。已加最小权限，但建议在发布前 pin SHA 并通过 Dependabot/Renovate 更新。

### Medium 风险

1. 两个上游 source 均有更新：
   - deepseek-harness：`47f94385 → 99f6f02f`
   - gstack：`008dd65b → c86e6472`
   本轮只执行 `--check/--dry-run`，未运行 destructive `--execute --yes`。
2. `INTEGRATION.md` 当前是 17 行 historical pointer，但 README 把它描述为 full integration plan，信息架构仍需统一。
3. `docs/AUDIT.md` 是旧审计，未显著标注被新报告取代。
4. Skills 仍有不少上游专用 `pnpm`、`bun`、`gh`、`glab`、`model` 命令，应明确 prerequisite/fallback。

## 7. Git 与交付说明

本轮未创建 Git commit。原因是审计开始时已有大量用户修改，并且本轮修复与用户正在修改的安装器、配置、README 等文件重叠。直接提交会混入无法可靠区分的既有改动。建议用户先审阅 `git diff`，再按逻辑拆分提交。

最终主验证日志和隔离行为日志均保存在 Jcode scratch，未把临时测试 fixture 留在仓库中。
